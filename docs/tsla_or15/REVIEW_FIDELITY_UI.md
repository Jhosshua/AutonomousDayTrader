## Findings requiring correction

1. **High — an invalid model fill/exit bar can create a valid-looking completed trade.** `backend/app/core/or15_execution.py:46` calls `_enter()` and `_offline_exit()` before `on_completed_bar()` validates the bar. If the position closes on that bar, validation then returns immediately because the phase is `CLOSED`. An isolated run through the actual `handle_bar_event` path used a valid setup followed by a T+2 bar with open 102, high 103, low **-1**, close 102. It recorded a STOP trade from 102 to 99 with `phase=CLOSED`, `reason=None`, and `incomplete=False`. Validate identity, chronology, completion and OHLCV before using a model bar's open or range; mark invalid holding data incomplete and never manufacture an exit from it. Preserve the terminal-open-before-high/low convention after validation.

2. **Withdrawn as a defect — offline replay does not exercise the durable inbox.** My initial review incorrectly claimed that attaching `TradingStateStore` to ordinary simulation would cause `ORDER_INTENT_NOT_DURABLE`. Both `_begin_durable_event()` and `_checkpoint_runtime()` intentionally bypass persistence when `simulation_mode=True`, so that failure does not occur through the standard path. I had not reproduced it. The valid remaining observation is an acceptance coverage gap: normal deterministic model tests cannot establish the actual inbox and checkpoint behavior. Test that behavior separately with an isolated store, production-mode ingestion and an injected clock/HTTP transport; do not change production persistence solely to accommodate the withdrawn claim.

3. **High — bulk Close all omits a staged OR15 setup.** `backend/app/main.py:3012` builds bulk-flatten targets only from positions, working orders and brackets. OR15 `WAITING_ENTRY` has none of those, so the dashboard action can finish with no position and still allow the scheduled buy afterward. Include an OR15 reservation in the target set. The existing per-symbol `_execute_manual_flatten` branch already knows how to consume that pending setup as `MANUAL_CANCEL`.

4. **High — the promised OR15 recovery invariants are absent.** `restore_runtime_state()` checks the version and source hash, and correctly allows only the known four-to-five-strategy migration. Its final `validate_runtime_state(account, engine, bracket_manager)` still has no strategy lifecycle state and cannot reject contradictory signal latches, wrong entry ids/deadlines, an OR15 position owned by an incompatible strategy phase, a changed ORL/2R, a two-share OR15 position with a matching two-share generic stop, or an unexplained terminal-session working entry. Add explicit OR15 restoration validation while allowing intended recoverable transitions such as a persisted entry intent and unresolved protection. Test a valid legacy migration and restart at each lifecycle phase, plus deliberate invariant violations.

5. **Medium — a valid zero-volume early QQQ bar rejects the entire session.** `tsla_or15_retest.py:167` computes VWAP and rejects zero cumulative volume at every opening minute, including 09:30. The contract accepts nonnegative bar volume and requires a defined cumulative VWAP at a candidate signal. A zero-volume early bar followed by ordinary volume has a valid later cumulative VWAP. A pure probe confirms the first zero-volume QQQ bar immediately produces `SKIPPED / ZERO_QQQ_VOLUME`. Keep VWAP undefined until cumulative volume becomes positive, then reject only when that unavailable value is actually required for signal evaluation.

6. **Medium — the active trade is presented as finished.** `tsla_or15_retest.py:277` includes `signal_consumed` in `done`, so `WAITING_ENTRY`, `ENTERING`, `HOLDING` and `EXITING` return `DONE_FOR_DAY`. `StrategyCard` consequently shows the “Done today” badge and resting treatment while the holding text reports an active position. A pure probe confirms `HOLDING → DONE_FOR_DAY`. Give the unresolved and holding phases explicit display states/badges; keep `can_open_now=false` without telling the operator the trade has finished. The exact hours, fifth-card styling, fixed-stop disabled button, target and deadline fields otherwise follow the existing UI framework.

7. **Medium — the selected data-continuity contract stops checking after a signal.** `on_time_tick()` checks missing required minutes only in the range/breakout/retest phases. After a valid signal, a clock tick at T+2 leaves `WAITING_ENTRY` unchanged even if neither intervening TSLA nor QQQ minute was received. A fresh quote can then trigger production entry. This differs from the implementation plan's declared contiguous same-session data requirement. State precisely which completed bars remain required between signal and entry and enforce that policy before entry without accidentally requiring T+2's still-incomplete OHLCV or violating the frozen five-second entry window.
